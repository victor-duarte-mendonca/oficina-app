# RFC 0002 — Escolha do banco de dados e ajustes no modelo relacional

- **Status:** Aprovado (recomendação adotada)
- **Detalhe de implementação:** [`specs/01-modelagem-banco.md`](../../specs/01-modelagem-banco.md); ER em [`../erd.md`](../erd.md)
- **Referenciado por:** README de `oficina-infra-database`

## 1. Problema

Justificar formalmente o banco de dados da Fase 3 e os ajustes do modelo relacional para **consistência** e **performance**, num
domínio que ganhou múltiplas unidades e um consumidor novo (a função de autenticação).

## 2. Natureza do domínio

O núcleo é a **Ordem de Serviço**: uma máquina de estados (`RECEIVED → IN_DIAGNOSIS → AWAITING_APPROVAL → IN_EXECUTION → FINISHED →
DELIVERED`, com `CANCELLED` transversal) que agrega itens de serviço e peças, debita estoque e calcula o valor total. Três características
decidem a persistência:

1. **Invariantes multi-tabela em uma transação.** Aprovar um orçamento debita `parts.stock_quantity`, insere em `work_order_parts` e muda
   `work_orders.status`: ou tudo acontece, ou nada. Consistência **forte**, não eventual.
2. **Concorrência sobre o mesmo agregado.** Dois mecânicos consumindo a mesma peça é *lost update* clássico; a solução (`parts.version`,
   lock otimista) depende de transação ACID.
3. **Consultas relacionais por natureza.** Os dashboards de R7 (volume diário, tempo médio por status) são agregações com junção entre
   `work_orders`, `clients` e `vehicles`.

## 3. Opções

| Opção | Avaliação |
|---|---|
| **Amazon RDS PostgreSQL 16 (`db.t4g.micro`)** | ACID, gerenciado (atende o requisito literal), ~US$0,016/h, criptografia em repouso, índices parciais e advisory lock que o Flyway usa |
| DynamoDB | Transações limitadas a 100 itens e sem junção; dashboards exigiriam desnormalização e consistência escrita à mão |
| MongoDB / DocumentDB | A OS cabe num documento, mas `parts` e `service_items` são catálogos compartilhados (duplicação e atualização em cascata); DocumentDB tem piso de ~US$50/mês |
| Aurora Serverless v2 | Piso de 0,5 ACU ≈ US$43/mês, cobra ocioso e **não para com o "End Lab"** |
| MySQL gerenciado | Viável, sem vantagem; perderia índice parcial e `GENERATED BY DEFAULT AS IDENTITY` já em uso |
| PostgreSQL em container no cluster | Mais barato, mas o PDF exige **banco gerenciado** |

## 4. Recomendação

**Amazon RDS PostgreSQL 16**, privado (`publicly_accessible = false`), TLS obrigatório (`rds.force_ssl=1`). Trade-offs de laboratório
assumidos e documentados: `multi_az = false`, `backup_retention_period = 0`, `deletion_protection = false` (em produção real: Multi-AZ,
backups e proteção de exclusão).

## 5. Ajustes no modelo (migrations `V5` e `V6`)

| Tipo | Ajuste | Razão |
|---|---|---|
| Requisito | `clients.status` (`ACTIVE`/`INACTIVE`/`BLOCKED`) + índice parcial `(cpf_cnpj) WHERE status='ACTIVE'` | R3 pede "existência **e status**" do cliente; o índice parcial é menor e mais quente em cache que o completo |
| Consistência | `TIMESTAMP` → `TIMESTAMPTZ` em todas as datas | a oficina expandiu para **múltiplas unidades**; sem fuso não se compara unidades nem se calcula o tempo médio por status |
| Consistência | `work_orders.order_number NOT NULL` | `NULL` escapa do `UNIQUE`: dá para ter N ordens sem número |
| Consistência | `CHECK` de domínio (valores ≥ 0, quantidades > 0, ano 1900–2100, lista dos 8 status, e-mail em minúsculo) | hoje garantidos só na aplicação, ausentes para o Lambda e para consultas manuais |
| Performance | `DROP` de `idx_clients_cpf_cnpj` e `idx_vehicles_plate` | cópias dos índices que o `UNIQUE` já cria; encarecem todo `INSERT`/`UPDATE` |
| Performance | índices de FK ausentes (`work_order_parts(part_id)`, `work_order_services(service_item_id)`) | sem eles, todo `DELETE`/`UPDATE` no pai faz *seq scan* nos filhos |
| Performance | `work_orders(created_at DESC)`, `(status, created_at DESC)`, `(client_id, created_at DESC)` | as duas consultas de R7 e o `GET /me/work-orders` |
| Segurança | papel `oficina_auth_ro` com `SELECT` por coluna (`id, name, cpf_cnpj, client_type, status`) | o Lambda, exposto à internet, não deve poder `DROP TABLE` nem ler `email`/`phone` (ADR 0005) |

Ownership: a instância é do `oficina-infra-database`; o **schema** é da aplicação ([ADR 0014](../adr/0014-migrations-pertencem-a-aplicacao.md)).
Pool de conexões: 8 por pod (4 × 8 = 32) para ficar abaixo do teto de ~112 do `db.t4g.micro`, junto da concorrência reservada do Lambda.

## 6. Riscos e pontos em aberto

- **Single-AZ e sem backup:** perda de dados aceita no laboratório. Validar na sessão AWS que as migrations `V1`–`V6` rodam num RDS real
  com `sslmode=require`.
- O `GRANT` por coluna e a senha do papel dependem de placeholder do Flyway: a senha precisa ser a mesma na aplicação e no Lambda.

## 7. Contestação

Se o domínio passasse a ter leitura analítica pesada ou múltiplas regiões, valeria avaliar réplica de leitura ou um modelo analítico
separado (CQRS), hoje sem requisito que o justifique.
